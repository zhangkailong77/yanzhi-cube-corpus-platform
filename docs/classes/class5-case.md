# 第五类别：案例与实践类

## 类别说明

**定义**：真实或标准化的跨境贸易案例，包含结论或经验

**目标**：积累案例库，供学习和参考，支持企业决策和风险防范

---

## JSON格式定义

### 文件命名规范
```
case_{语言代码}.json

语言代码：
- zh: 中文
- en: 英语
- th: 泰语
- ms: 马来语
- vi: 越南语
```

### JSON结构模板

```json
{
  "meta": {
    "version": "1.0",
    "corpus_type": "case",
    "language": "zh",
    "domain": "trade",
    "created_by": "专家团队",
    "created_at": "2024-01-15T10:00:00Z",
    "description": "案例与实践库 - 中文"
  },
  "data": [
    {
      "case_id": "CASE-001",
      "case_title": "某跨境电商企业因HS编码申报错误被海关处罚",
      "case_type": "失败教训",
      "background": "某跨境电商企业主营电子产品出口，月出口额约500万美元",
      "situation": "企业将某电子产品误归入低税率税目",
      "outcome": "补缴关税50万元，被记录信用不良",
      "conclusion": "HS编码申报错误导致补税和信用受损，企业应建立严格的归类复核机制",
      "tags": ["合规", "HS编码", "风险管理"]
    }
  ]
}
```

---

## 字段说明

### 顶层 meta 字段

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `version` | string | 是 | 版本号（如：1.0） |
| `corpus_type` | string | 是 | 语料类型（固定值：case） |
| `language` | string | 是 | 语言代码（zh/en/th/ms/vi） |
| `domain` | string | 是 | 业务域（trade/customs/payment/logistics等） |
| `created_by` | string | 是 | 创建者/团队 |
| `created_at` | string | 是 | 创建时间（ISO 8601格式） |
| `description` | string | 是 | 语料描述 |

### 案例记录字段

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `case_id` | string | 是 | 案例唯一标识符（如：CASE-001） |
| `case_title` | string | 是 | 案例标题 |
| `case_type` | string | 是 | 案例类型（成功/失败/特殊） |
| `background` | string | 是 | 案例背景 |
| `situation` | string | 是 | 情况描述 |
| `outcome` | string | 是 | 最终结果 |
| `conclusion` | string | 是 | 案例总结/结论 |
| `tags` | array | 否 | 标签列表，便于分类和检索 |

---

## 案例类型分类

### case_type 字段的可选值

```
1. 成功案例：成功的业务实践、成功案例经验
2. 失败教训：失败的业务实践、错误教训
3. 特殊案例：特殊情况处理、边界情况、复杂案例
```

---

## conclusion 与 outcome 的区别

### outcome（最终结果）
- **定义**：案例中实际发生的结果
- **特点**：描述客观、具体、事实性
- **示例**：
  - "补缴关税50万元，被记录信用不良"
  - "关税成本降低10%，产品竞争力提升"
  - "货物顺利清关，客户满意度提升"

### conclusion（案例总结/结论）
- **定义**：从案例中总结的经验、教训、启示
- **特点**：描述主观、抽象、指导性
- **示例**：
  - "HS编码申报错误导致补税和信用受损，企业应建立严格的归类复核机制"
  - "充分利用RCEP原产地规则和累积机制，可以有效降低跨境成本"
  - "信用证支付可以降低收汇风险，但需注意条款细节"

### 关键区别

| 维度 | outcome | conclusion |
|------|---------|------------|
| 性质 | 客观结果 | 主观总结 |
| 内容 | 发生了什么 | 学到什么 |
| 用途 | 记录事实 | 指导决策 |
| 时效性 | 案例发生时 | 持续有效 |

## 多语生成策略

### 源语言策略
- **源语言**：中文
- **语料来源**：专家编写的200条案例
- **质量保证**：由业务专家审核，确保案例真实性和结论准确性

### 翻译策略

#### 1. 翻译方式
- **英语**：AI翻译 + 人工校对（建议抽检20%）
- **泰语**：AI翻译 + 人工校对（建议抽检30%）
- **马来语**：AI翻译 + 人工校对（建议抽检30%）
- **越南语**：AI翻译 + 人工校对（建议抽检30%）

#### 2. case_id保持一致
- 所有语言的案例保持相同的`case_id`（如CASE-001、CASE-002等）
- 便于跨语言查询同一案例
- 便于多语言案例库使用

#### 3. 翻译Prompt模板

```
作为跨境贸易专家，请将以下中文案例翻译为[目标语言]。

要求：
1. 准确翻译专业术语（参考术语库）
2. 保持案例叙述的一致性和逻辑性
3. conclusion字段要体现总结性和指导性
4. 表达地道、专业、自然

中文案例：
{
  "case_id": "CASE-XXX",
  "case_title": "[案例标题]",
  "case_type": "[案例类型]",
  "background": "[背景]",
  "situation": "[情况]",
  "outcome": "[结果]",
  "conclusion": "[总结]",
  "tags": ["标签1", "标签2"]
}

请返回目标语言的JSON格式。
```

### 翻译质量控制

#### 1. 专业术语翻译一致性
- 使用第一类别"术语与标准表达类"的术语库
- 关键术语（如HS编码、信用证、RCEP等）保持一致性
- 缩写术语保留英文（如RCEP、REACH等）

#### 2. 叙述一致性
- `background`、`situation`、`outcome`保持叙述一致
- 时间线逻辑清晰
- 因果关系明确

#### 3. 结论翻译准确性
- `conclusion`要体现总结性和指导性
- 与`outcome`有明确区分
- 便于读者学习和应用

#### 4. 人工抽检标准
- **英语**：抽检20%，重点关注术语准确性和表达地道性
- **泰语/马来语/越南语**：抽检30%，重点关注语法、词汇准确性
- 抽检记录：记录抽检结果，用于后续AI模型优化

## 与其他类别的关联

### 与第一类别（术语类）的关联
- **术语一致性**：案例中的术语与术语库保持一致
- **翻译参考**：使用术语库的translations作为翻译参考

### 与第二类别（问答类）的关联
- **案例问答化**：可以将案例扩展为问答形式
- **经验提取**：从案例中提取经验教训，形成问答

### 与第四类别（流程规则类）的关联
- **规则案例化**：可以将规则用实际案例说明
- **案例规则化**：从案例中提取规则，形成流程规则

### 跨类别复用示例

#### 从问答类提取案例
```
问答库 QA-004（中文）:

  ├── background: "某跨境电商企业主营电子产品出口..."

  ├── outcome: "补缴关税50万元，被记录信用不良"

```

## 数据验证规则

### 通用验证规则
1. **JSON格式验证**：文件必须是有效的JSON格式
2. **字段类型验证**：所有字段类型必须符合定义
3. **必填字段验证**：必填字段不能为空或null
4. **唯一性验证**：case_id必须在文件内唯一
5. **枚举值验证**：case_type、language等字段必须在定义的范围内
6. **格式验证**：日期、时间等格式必须正确（如created_at使用ISO 8601格式）

### 案例特定验证规则
1. **case_id格式**：必须符合 CASE-XXX 的格式（XXX为数字）
2. **case_title长度**：案例标题不能少于10个字符
3. **background长度**：案例背景不能少于20个字符
4. **situation长度**：情况描述不能少于20个字符
5. **outcome长度**：结果描述不能少于10个字符
6. **conclusion长度**：总结描述不能少于20个字符
7. **case_type枚举**：必须是预定义的案例类型（成功/失败/特殊）

## 注意事项

1. **case_id命名**：必须保持跨语言一致，便于多语言案例库使用
2. **术语一致性**：案例中的术语与术语库保持一致
3. **outcome与conclusion区分**：outcome描述客观结果，conclusion描述主观总结
4. **tags分类**：建议使用预定义的标签分类，便于检索
5. **case_type分类**：必须使用预定义的案例类型（成功/失败/特殊）
6. **叙述逻辑**：background、situation、outcome要有清晰的逻辑关系
7. **conclusion指导性**：结论要具有指导性和可操作性
8. **人工校对**：英语20%，其他语言30%，确保翻译质量
9. **跨类别复用**：可从问答类、流程规则类提取案例，提高效率
10. **文件命名**：严格按照 case_{语言代码}.json 格式命名

## 案例编写建议

### 1. background（案例背景）
- 明确案例的背景信息
- 提供必要的上下文
- 简洁明了

**好的示例**：
- "某跨境电商企业主营电子产品出口，月出口额约500万美元" ✅

**不好的示例**：
- "一个企业" ❌（信息不够）
- "某企业做出口生意很多年了" ❌（不够具体）

### 2. situation（情况描述）
- 描述案例中发生的具体情况
- 突出关键问题和挑战
- 客观准确

**好的示例**：
- "企业将某电子产品误归入低税率税目" ✅
- "通过优化供应链，使原产地累积达到RCEP要求" ✅

**不好的示例**：
- "搞错了" ❌（不够具体）
- "优化了" ❌（不够详细）

### 3. outcome（最终结果）
- 描述案例的客观结果
- 具体明确，包括数据和影响
- 事实性描述

**好的示例**：
- "补缴关税50万元，被记录信用不良" ✅
- "关税成本降低10%，产品竞争力提升，订单量增长15%" ✅

**不好的示例**：
- "损失了" ❌（不够具体）
- "好了" ❌（不够详细）

### 4. conclusion（案例总结）
- 提炼经验教训和启示
- 具有指导性和可操作性
- 主观总结，但要有依据

**好的示例**：
- "HS编码申报错误导致补税和信用受损，企业应建立严格的归类复核机制" ✅
- "充分利用RCEP原产地规则和累积机制，可以有效降低跨境成本" ✅

**不好的示例**：
- "要注意" ❌（不够具体）
- "好的" ❌（没有指导性）

## 去掉 lessons_learned 的原因

### 原因1：避免重复
- `conclusion` 字段已经承担了经验总结的作用
- `lessons_learned` 与 `conclusion` 功能重叠
- 保留两个字段会导致信息冗余

### 原因2：简化结构
- 去掉 `lessons_learned` 后，字段数量从9个减少到8个
- 结构更简洁，便于维护
- 降低数据录入复杂度

### 原因3：聚焦核心
- `conclusion` 字段更灵活，可以包含各种总结内容
- 包括经验教训、启示建议、最佳实践等
- 不需要单独的 `lessons_learned` 字段
